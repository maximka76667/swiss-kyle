# E2E: Every CI Session Creation Times Out (Two Unrelated Causes, One Per OS)

**Type**: issue
**Summary**: The e2e suite passed 100% of the time run locally but failed every single spec in GitHub Actions on both matrix legs with `WebDriverError: ... timeout ... POST /session`. Linux is resolved: `tauri-driver` started before any display existed. Windows is closed as won't-fix for now: three unrelated theories (driver/runtime version mismatch, an app-side setup() hang, WebView2 GPU-process hang) were each tried and disproven or ineffective; Windows dropped from the `e2e` CI job entirely (`rust-unit-tests` keeps running on Windows — unaffected, no WebView2 involved).

## Overview

The CI workflow (`.github/workflows/ci.yml`) was added recently. Its first real runs failed every spec file, on both `ubuntu-22.04` and `windows-latest`, with `webdriver`/`@wdio/runner` logging a `WebDriverError` for `POST http://127.0.0.1:4444/session` timing out (~2 minutes per attempt), then `[after hook] window already closed, skipping: TypeError: browser.execute is not a function` (a session that never opened has no `browser` to call). This is a different failure shape from [[wiki/issues/webview2-session-crash-on-fast-relaunch]]: that issue is an intermittent crash of the *next* session shortly after a *previous* one tears down. Here, every session failed outright, including the very first spec of the run, which has no previous session to have crashed from.

## Details

Both platforms share one proximate symptom — `tauri-driver` (listening on port 4444, confirmed reachable since `wdio.conf.ts`'s `waitForPort(4444)` in `onPrepare` didn't throw) never responds to a new-session request — but for two unrelated reasons:

**Linux — no display when `tauri-driver` starts.** `onPrepare` in `wdio.conf.ts` spawns `tauri-driver` directly (`spawn("tauri-driver", [])`) once, in the WDIO *launcher* process, before any worker exists. `ci.yml` installs `xvfb` as an apt package and relies on WDIO's built-in `@wdio/xvfb`, which auto-wraps each spec file's *worker* process in `xvfb-run` (visible in the logs as `@wdio/xvfb:ProcessFactory: Creating worker process with xvfb-run wrapper`) — but the launcher process, and everything it spawns (`tauri-driver`, and the `app` binary `tauri-driver` in turn launches), is never covered by that wrapping. With no `DISPLAY`, WebKitGTK can't initialize, so the app/`WebKitWebDriver` never becomes ready, and `tauri-driver` never answers the session POST. Tauri's own official CI recipe confirms this: it wraps the *entire* test command in `xvfb-run` (`xvfb-run yarn test`), not a per-worker mechanism, specifically so the display exists before `tauri-driver` itself starts.

**Windows — the preinstalled `msedgedriver` doesn't match the app's WebView2 Runtime version.** The Windows failure log is shaped differently from Linux's plain timeout: after ~60s, `webdriver` logs `WebDriverError: session not created: DevToolsActivePort file doesn't exist`, retries once, then times out for good on the retry. That message comes from `msedgedriver` itself (so a driver *was* found and *did* run — `windows-latest` images preinstall one at `C:\SeleniumWebDrivers\EdgeDriver`, already on `PATH`), reporting that the browser process it launched never opened its DevTools debugging port within the driver's own internal timeout — i.e. the app's WebView2 host failed to come up under that specific driver. The preinstalled driver is provisioned to match the machine's standalone **Edge browser app** version, but `tauri-driver` drives the **WebView2 Runtime** embedded in `app.exe` — a separately-versioned, independently-auto-updating component that routinely drifts out of sync with the Edge app version on the same machine. A version-mismatched `msedgedriver` against WebView2 is a documented cause of exactly this error. `ci.yml`'s `e2e` job never installed a WebView2-version-matched driver — only `tauri-driver` itself — so it fell back to whatever preinstalled, possibly-mismatched driver happened to be on `PATH` first.

## Decisions & Rationale

Fixed by matching Tauri's own documented CI recipe rather than guessing:

- **Linux**: `ci.yml`'s "Run e2e suite" step is now split by OS; the Linux leg runs `xvfb-run --auto-servernum bun run test:e2e`, wrapping the whole step (launcher process included) so a display exists before `onPrepare` ever spawns `tauri-driver`. `@wdio/xvfb`'s own per-worker wrapping is left in place (harmless, redundant once a display already exists) rather than disabled.
- **Windows**: a new "Install msedgedriver" step runs `cargo install --git https://github.com/chippers/msedgedriver-tool` then the tool itself, which — unlike the generic driver GH preinstalls — detects the runner's actual **WebView2 Runtime** version and downloads the matching `msedgedriver.exe` into the working directory; that directory is then added to `$GITHUB_PATH` ahead of the preinstalled one (`GITHUB_PATH` entries are prepended for later steps) so `tauri-driver` picks up the correctly-matched driver instead.
- Added a "Print driver/runtime versions" step on both platforms, right before "Run e2e suite", printing `tauri-driver`/`msedgedriver`/`WebKitWebDriver` versions, every `msedgedriver.exe` found on `PATH` in resolution order, and the actual WebView2 Runtime version from the registry. A session-creation timeout on its own carries no version info — this exists so that info is in the log on the very next failure, instead of needing another ~12-minute round trip just to learn what versions were in play.

## Update (2026-08-19): Windows version-mismatch theory ruled out

The "Print driver/runtime versions" step's first real output disproved the version-mismatch theory directly: the `msedgedriver-tool`-downloaded driver, the preinstalled `C:\SeleniumWebDrivers\EdgeDriver` one, and the actual WebView2 Runtime (read from the registry) were all `151.0.4129.72` — an exact match, on the very run that still failed identically (`DevToolsActivePort file doesn't exist`). So the driver was never the problem; the real cause is still open.

Investigated further by reading `tauri-driver`'s actual source (`tauri-apps/tauri`, `crates/tauri-driver/src/{main,webdriver}.rs`, moved there from the old `tooling/webdriver` path): on Windows, `msedgedriver.exe` — not `tauri-driver` and not anything `wdio.conf.ts` spawns directly — is what launches `app.exe` (via the `ms:edgeOptions.binary` capability). `tauri-driver` explicitly sets `.stdout(Stdio::null())` on the `msedgedriver` child (stderr is left inherited, deliberately, "so WebDriver logs/errors are still visible" per its own comment) — meaning `app.exe`'s own stdout was never reaching anything we could see, regardless of how `tauri-driver` itself was spawned. Confirmed the debug build's `tauri_plugin_log` (`Builder::default()` in `src-tauri/src/lib.rs`) also writes to a file in the OS log directory independently of stdout, so that file — not stdout — is the way to actually see what the app was doing when a session hangs.

Also relevant, found via research rather than confirmed yet: Tauri v2's window (declared in `tauri.conf.json`, not built manually in code) is created only once the event loop starts, which only happens after `.setup()` returns — so if `.setup()` (in `src-tauri/src/lib.rs`, which does a blocking up-to-10s NATS-connect retry loop and several `resolve_bin`/sidecar-spawn calls, each `unwrap_or_else`-routed to `fatal()` on failure) never returns, the window — and therefore WebView2's DevTools port — never gets created at all. `fatal()` calls `.blocking_show()` on a native error dialog and blocks the calling thread until it's dismissed; on a non-interactive CI session nothing can dismiss it, which would hang indefinitely — well past any driver-side timeout. This is a plausible mechanism, not a confirmed one; the log file is what will actually confirm or rule it out.

Fixed two blind spots so the next failure is diagnosable instead of another guess-and-check round trip:
- `e2e/wdio.conf.ts`'s `onPrepare` used to spawn `tauri-driver` with `stdio: "ignore"`, discarding its stderr (which includes `msedgedriver`'s own, per above). Changed to pipe both streams to the wdio process's own stdout/stderr, prefixed `[tauri-driver]`.
- `.github/workflows/ci.yml` now has an `if: always()` step per OS that reads and prints every file under the app's log directory (`$LOCALAPPDATA\com.swiss.kyle\logs` on Windows, `~/.local/share/com.swiss.kyle/logs` on Linux) after the suite step, so it runs even on a timeout — this is expected to be the one that actually answers the question.

## Known Issues / Tech Debt

**Linux fix confirmed**: the first CI run after the `xvfb-run` change (2026-08-19) passed cleanly.

**Windows fix did not resolve it on the first attempt, and the diagnosis it was based on turned out wrong.** A run after the `msedgedriver-tool` step was added reproduced the exact same `session not created: DevToolsActivePort file doesn't exist` failure, on every spec, unchanged. Initially suspected a silent failure in the fix itself — `pwsh` doesn't fail a step just because a native `.exe` it calls exits non-zero, so a broken `cargo install`/download could pass the step green while quietly falling back to the wrong driver — and hardened the step with explicit `$LASTEXITCODE` checks accordingly (harmless to keep regardless). But the hardened step's own diagnostic output (see Update below) showed the download actually succeeded and was version-correct, which disproved the version-mismatch theory outright, not just the "silent failure" one.

Reading the app's own log file (`Print app log file (Windows)`, added specifically to answer this) settled the two remaining theories at once: across an entire ~23-minute run (6 specs × up to 2 attempts each), exactly one launch ever wrote anything at all, and that one reached full Rust-side readiness (`worker N: Worker N ready, entering fetch loop`) — yet its session still failed identically. That rules out both a `.setup()` hang (the app can and did fully start) and NATS as the actual cause (the NATS bind failure visible in that log was itself a downstream symptom — a port collision from an earlier attempt's orphaned process, not something present on a clean first attempt). It isolates the problem to WebView2 itself never exposing its remote-debugging port under `msedgedriver`, independent of the app's own health.

Tried `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS: --disable-gpu` next, on the theory that this matches a known, tracked upstream issue — [tauri-apps/tauri#2530](https://github.com/tauri-apps/tauri/issues/2530), WebView2 stuck at 100% CPU with a blank window specifically on virtualized Windows (QEMU/VirtualBox tested there; GitHub-hosted `windows-latest` runners are also VMs) — since a GPU-process hang would produce exactly this symptom: host process alive and healthy, browser subprocess never finishes initializing. This also failed identically (2026-08-19, run started 13:35 UTC).

**Decision: Windows dropped from the `e2e` job (2026-08-19).** Three independent, mechanistically distinct fixes (driver/runtime version match, ruling out an app-side hang, disabling GPU acceleration) all failed to change the symptom at all — same error, same timing, every time. That pattern — nothing changes anything — points at something more fundamental about `tauri-driver`+WebView2 in this specific hosted-VM environment than any of these theories, and is a strong signal to stop spending further investigation time here rather than continue guessing. `rust-unit-tests` still runs on Windows (plain `cargo test`, no WebView2 involved, unaffected). Revisit if `tauri-apps/tauri#2530` or an equivalent upstream issue gets a real fix, or if a different Windows WebDriver approach (e.g. `@wdio/tauri-service`'s auto-managed driver, or the "attach" approach with a manually-set `--remote-debugging-port`) seems worth trying.
